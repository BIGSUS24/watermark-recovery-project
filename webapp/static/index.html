Identification

Two ways to fix a tampered file, and they are not the same guarantee. Exact restore uses the watermark only to prove which library record this is and to pinpoint exactly which blocks changed — the pixels themselves then come straight from that archive copy, byte for byte. Rebuild from watermark only needs no archive at all: it reconstructs the damaged blocks purely from the recovery data hidden inside the surviving pixels, which is the only option when there is nothing on file to restore from, and it is approximate, never bit-exact.

How it works

The whole scheme in four steps, and the limits that come with it.

The scheme, running

drag to orbit

  • intact block
  • the two hidden bit planes
  • flagged: signature no longer matches
  • unrecoverable: its backup died too
01

Split every 8×8 block's budget in two

Each block gets 128 hidden bits: a 32-bit keyed signature of itself, and a 96-bit compressed backup of a different, far-away block.

02

Hide them in the two lowest bits

Only the two least-significant bits of each pixel change, so the image looks identical — around 43 dB PSNR. The signature covers the six upper bits, so embedding can never invalidate itself.

03

Detect by recomputation

Verification recomputes every signature from the pixels in front of it. A mismatch means that exact block changed. The signature is bound to the image's identity and the block's position, so a valid signature moved elsewhere still fails.

04

Repair from the surviving backup

Each flagged block is rebuilt from the backup held by its intact partner. If that partner was destroyed too, the block is marked unrecoverable rather than filled with invented pixels.

Honest limitations

  • Protect almost anything; verify only what survived losslessly. The watermark lives in the two least-significant bits of every pixel. Protecting accepts PNG, JPEG, PDF, BMP, TIFF, WebP, or GIF as a source — the file handed back is always a fresh, lossless PNG. Verifying is stricter by necessity: it only accepts PNG, BMP, TIFF, or PDF, because JPEG, WebP, and GIF all re-encode pixels lossily and overwrite exactly the bits the watermark lives in. A deliberately fragile watermark working as designed, not a bug.
  • Only images it protected first. There is nothing to verify in an image that was never watermarked, which is why the library exists.
  • Repair is an approximation. Recovery rebuilds a low-frequency version of what was destroyed — visibly softer, never pixel-perfect.
  • Resizing or cropping breaks it. The block grid no longer lines up, so verification fails everywhere rather than pointing at a region.
  • The demo key sits next to the image. Fine for a local tool, wrong for deployment: real systems keep keys in a keyring or HSM, never beside the file they authenticate.
