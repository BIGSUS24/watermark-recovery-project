@@SEC 4.1 Database Requirements

The core scheme is stateless. Verification needs only the received image, the secret key and the image identifier, with no original image, no reference database and no network call, so a third party holding the key can repeat any verdict on an isolated machine. Persistence exists only for the local web application, which keeps a library of protected images for retrieval and re-verification. The library is a single SQLite table named protected, held in the file webapp/library.db. Table 4.1 gives its schema.

[[TABLE 4.1]]

Each row records one protected image. The columns name, created_at, height, width, block and variant describe it and its protection configuration; image_id holds the identifier bound into every authentication tag, png the protected image as a lossless PNG, and sha256 its digest. The nullable columns psnr, ssim and blocks record quality figures measured at protection time. Two indexes, idx_shape on (height, width, block) and idx_sha on sha256, serve lookups by geometry and by content digest.

One field is security-relevant. The key column stores the secret key beside its image, and the key_encrypted flag, which defaults to zero, records whether it is stored encrypted. Storing the key beside the image is acceptable only for a single-user local demonstration, where the person who protects an image is the person who verifies it and the database file never leaves the machine. In any deployment the key would have to move to an external key store, because anyone able to read the database could re-embed a forged image. This limits the demonstration application, not the scheme.

Retention is soft. The deleted_at column is null for a live record and holds a timestamp once the user deletes it, so a record can still be audited after removal; the stored image bytes therefore persist after deletion, a privacy consideration beyond the demonstration. Nothing else depends on the database, and losing the file does not affect verification of any exported image whose key is known.

@@SEC 4.2 Software Requirements (Platform Choice)

The platform keeps the trust path short and the evaluation reproducible. Python is the implementation language because the scientific stack lives there and its standard library supplies hashlib, hmac and struct, so the keyed SHA-256 construction [20] is computed, and the payload bits packed, with no third-party cryptographic dependency. The minimum interpreter version is Python 3.10. An auditor therefore has one fewer package to review before trusting a positive detection, which is the property the scheme exists to provide.

NumPy 2.1.2 provides the vectorized block arithmetic on which the per-block cost depends. OpenCV-headless 5.0.0.93 and scikit-image 0.26.0 supply the transforms and the SSIM implementation [21], and Pillow 10.4.0 handles lossless formats such as PNG, BMP and TIFF without re-encoding. Matplotlib 3.11.1 draws the evaluation figures. No library performs any part of the authentication.

Flask serves the local web application because it is small enough to audit in full, which matters for a tool holding secret keys. Streamlit 1.61.1 provides the demonstration interface over the same pipeline. SQLite stores the library because the requirement is one table on one machine, and a heavier database would add attack surface without adding any capability this project uses.

Every dependency version is pinned exactly so that the grid reproduces on another machine, as every corpus file is pinned by SHA-256. No machine-learning framework appears in the stack and the scheme has no trained parameters, which is what allows any verdict to be repeated bit for bit. @@SEC 4.3 Hardware Requirements

The scheme needs any commodity x86-64 or ARM CPU and runs on a single thread. No GPU or other accelerator is used at any stage, including evaluation. Memory is bounded by the image itself plus one permutation of K integers, where K is the number of blocks, which is 4,096 for a 512x512 image at B = 8. Disk is needed only for the corpus and result grid, a few gigabytes in all.

Runtimes were measured on a commodity AMD x86-64 CPU, single thread, for a 512x512x3 image. Embedding takes 473 ms and verification takes 197 ms, less than half of embedding. These interpreted-implementation figures are reported as measured, not as a limit on the scheme. Table 4.3 summarizes the hardware requirements.

The scheme can therefore run inside an embedded capture device or a hospital gateway, where a learned detector cannot: it needs a trained model and usually a GPU, which fit neither a camera body nor a clinical network appliance. A deterministic scheme with a few hundred milliseconds of single-thread work per image fits both, and a gateway or an auditor can check images with the key alone on an ordinary laptop, with no inference runtime.

@@SEC 4.4 Analysis Models: SDLC Model to be Applied

The project follows an incremental and iterative model, not a waterfall, for an empirical reason. The payload design, the mapping construction and the descriptor variants were each validated against measurement before the next increment was built, and two defects found during adversarial testing of the web application fed back into the core library. Seven increments were delivered in sequence, each adding one capability to a pipeline that already ran end to end.

* Core payload and tag: key derivation, bit budget, MSB projection, the keyed tag and the descriptor encoding.
* Block mapping: the key-seeded single-cycle permutation with minimum-separation repair.
* Embedding and detection: LSB packing with shifting, and tag recomputation with block localization.
* Recovery: rebuilding flagged blocks from surviving partners and reporting the recoverability rate.
* Tamper harness and metrics: four tamper classes with exact ground-truth masks.
* Full grid and automated gate: the complete experiment and the sanity checks on its output.
* Applications: the Flask web application and the Streamlit demonstration interface.

Every increment ends in a runnable end-to-end test, and none is complete until the sanity gate runs clean on the results it produces. A finding from the harness or the gate returns to the earlier increment that caused it, which is corrected and re-verified before work moves forward. Fig. 4.1 shows the model as applied here.

[[FIG 4.1]]

A waterfall sequence would have served this project badly, discovering the tamper coincidence behavior only at the end, when the mapping design could no longer be changed. Under the incremental model it appeared while the mapping and recovery increments were still open, which is why the minimum-separation repair pass and the disclosure of the recoverability rate are part of the design and not afterthoughts.
