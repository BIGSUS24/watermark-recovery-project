@@SEC 5.1 System Architecture

The system is organized as four decoupled stages. Stage one is embedding, which runs at or near acquisition and turns an original image into a watermarked one. Stage two is distribution, during which the image may be stored, copied, transmitted and, in the adversarial case, tampered with; the harness simulates it with four tamper classes and exact ground-truth masks. Stage three is verification and localization, which any party holding the key can run at any later time. Stage four is recovery, which repairs flagged content where the surviving watermark allows. The stages communicate only through the image and a block mask, so each can be developed, tested and replaced independently. Stages one, three and four depend on the key; distribution needs no cooperation from the system, so an image can travel through ordinary channels provided they are lossless.

The decisive property of the architecture is what stage three does not need. Verification requires only the received image, the secret key and the image identifier: no original image, no reference database, no network call and no model weights. Every positive detection reduces to one recomputed keyed hash compared against a stored value, so a third party holding the key can repeat the decision bit for bit. This is the practical advantage of an active scheme inside an institutional custody chain.

Fig. 5.1 shows the data path. The upper row embeds: the original image I passes through block partition, descriptor encoding, the key-seeded block map and the keyed tag (HMAC) to give the watermarked image Iw. The lower row verifies and recovers: the received image I' passes through LSB extraction, tag recomputation and the tamper mask, then the recovery engine. A dashed path from Iw to I' represents distribution, and the key and identifier feed the block map and the tag.

[[FIG 5.1]]

The software mirrors this decomposition. The payload module is the foundation imported by all others, holding key derivation, the bit budget, the MSB projection, tag computation, descriptor coding and LSB packing. The blockmap module builds the key-seeded permutation, the embed, detect and recover modules implement stages one, three and four, and sanity_gate validates the grid that run_experiments produces before any table or figure is built; tamper and metrics support evaluation. Two applications sit over the same pipeline: a Flask web application with a SQLite library, and a Streamlit demonstration interface. Table 5.2 summarizes the responsibilities.

@@SEC 5.2 Mathematical Model

Let I in {0,...,255}^(MxN) be the host image, Ks the secret key and ID an image identifier. The image is partitioned into non-overlapping BxB blocks in raster order, and b_i denotes the i-th block for i = 0,...,K-1, with c(i) its center coordinate. Dimensions that are not a multiple of B are cropped rather than padded, so no synthetic content is ever authenticated. The model follows the order of use: bit budget, projection, mapping, descriptor, tag, and finally recoverability and cost.

The first quantity is block capacity. Two bit-planes of B^2 pixels give 2B^2 bits, of which the tag takes at most half and the descriptor the rest.

@@EQ cap(B) = 2B^2,   t(B) = min(32, cap(B)/2),   d(B) = cap(B) - t(B)

At B = 8 the triple (capacity, tag, descriptor) is (128, 32, 96) bits. At B = 4 the capacity falls to 32 bits and the tag shrinks accordingly, which is the cost of finer localization examined in the ablation. Table 5.1 gives the per-block budget, and Fig. 5.2 shows how the 128-bit payload is divided into a 32-bit authentication tag and a 96-bit recovery descriptor. The descriptor in turn consists of 12 quantized DCT coefficients of 8 bits each, and the whole payload is written into the two least-significant bit-planes of the block's 64 pixels.

A most-significant projection separates what is signed from what is overwritten.

@@EQ MSB(a) = a AND 0xFC

The projection zeroes the two least-significant bits of a pixel value and is idempotent. Embedding writes only to those two bit-planes, so it cannot alter the content that the tag was computed over. That is what makes the scheme single-pass: no embed-and-verify loop is needed, and the tag computed before embedding is the tag verification will recompute afterwards.

The block map decides which block carries which descriptor, and must satisfy three requirements.

@@EQ (R1) m bijective;   (R2) ||c(i) - c(m(i))||_2 >= d_min;   (R3) m is a single K-cycle

The separation is d_min = (1/4) min(M, N). R3 is obtained by construction, not rejection sampling. A cryptographically seeded Fisher-Yates shuffle produces a cycle order of the K blocks, and m is read off that order directly, sending each block to its successor in the cycle. Fixed points and mutual pairs are therefore impossible, and bijectivity holds without a check. A repair pass then enforces R2 by exchanging offending positions, after which all three properties are verified. Fig. 5.3 illustrates the result.

[[FIG 5.3]]

The descriptor is a low-frequency summary of the block's projected content. For Variant A it is the quantized leading portion of the transform.

@@EQ q_hat(i,l) = clip( round( C_i(sigma(l)) / Delta_l ), -128, 127 ),  l = 1,...,12

Here C_i is the orthonormal two-dimensional DCT of the level-shifted projected block, sigma(l) is the zig-zag index and Delta_l the step size of band l. No retained coefficient can clip. By the Cauchy-Schwarz inequality the magnitude of any coefficient is at most 1024 at B = 8, and every step size is large enough that the quantized magnitude stays inside the signed 8-bit range. Variant C uses the same 96-bit layout with an adaptive, rate-distortion-fitted allocation.

Authentication binds the block's content, its position and the descriptor it carries.

@@EQ a_i = Trunc_32( HMAC-SHA256_Ks( ID || i || MSB(b_i) || r_{m^-1(i)} ) )

The primitive is HMAC over SHA-256 [20], truncated to 32 bits. Each bound field answers a specific attack. MSB(b_i) makes the tag independent of the bits embedding will write, so the tag survives its own insertion. The block index i and the identifier ID defeat the collage attack of [7], in which blocks from different positions or different images are recombined because each block is authenticated in isolation. The last field, r_{m^-1(i)}, is the descriptor this block physically carries on behalf of another block; binding it prevents an attacker from replacing recovery data without detection, since any substituted descriptor changes the recomputed tag.

Recovery quality is summarized by the recoverability rate. With T the flagged set and U the subset of T whose partner is itself flagged,

@@EQ rho = 1 - |U| / |T|,   U = { i in T : m(i) in T }

A flagged block is unrecoverable exactly when the block carrying its descriptor is also flagged. If the position of m(i) were independent of the tampered region, that probability would equal the tampered fraction alpha, giving the structural bound E[rho] approximately 1 - alpha. The bound is a baseline of the one-to-one allocation, not a guarantee, and the evaluation chapter compares it with measured values.

Finally, the cost of the scheme is linear in the image size.

@@EQ T(M,N) = O(MN)

Embedding and verification each need one keyed hash and one BxB transform per block, plus O(K) work to build the mapping. There is no iteration, optimization or training, and no NP-hard sub-problem arises anywhere in the pipeline, so the problem is of class P. Memory is likewise proportional to the image; the only whole-image quantity is the permutation.

@@SEC 5.3 Data Flow Diagrams

The data flow diagrams decompose the system from its external boundary down to the detector and the recovery engine, each level refining the one above under the same names. The secret key is an input supplied by the user at each operation, not data owned by the pipeline.

[[FIG 5.5]]

@@SUB 5.3.3 Level 2

Fig. 5.6 decomposes 3.0 and 4.0 into 3.1 Extract LSB Payload, 3.2 Recompute Tags, 3.3 Compare and Build Block Mask, 3.4 Refine and Expand to Pixel Mask, 4.1 Partition Flagged Set, 4.2 Decode Partner Descriptor, 4.3 Write Recovered Pixels and 4.4 Mark Unrecoverable Blocks. Tags are compared per channel and combined by an OR rule, so a tamper touching any single channel flags the block. Refinement examines each unflagged block whose neighbors are mostly flagged, with a threshold that scales with the number of valid neighbors, so border blocks are not penalized. Flagged blocks with an intact partner are rebuilt from its descriptor; those whose partner is also flagged are marked explicitly, never inpainted and never left in place silently, so a viewer can always tell reconstructed from unrecovered content.

[[FIG 5.6]]

@@SEC 5.4 Entity Relationship Diagram

Fig. 5.7 shows the data model. The central entity is PROTECTED_IMAGE, with primary key id. Its attributes record the image and its protection configuration, the key with an encryption flag, the image bytes and content hash, the quality scores and a soft-deletion timestamp. In the implementation it is a single SQLite table with indexes on the image shape and on the hash.

Two further entities are drawn and marked conceptual. VERIFICATION_EVENT is related to PROTECTED_IMAGE one-to-many, since an image is embedded once under one key but may be checked repeatedly by different parties; KEY_PROFILE is related many-to-one, since many images may share one key. Only PROTECTED_IMAGE is persisted in the current build. The conceptual entities are drawn because an archive or ingest deployment would need a record of each verification and a managed key store, not because the software provides them: verification results are returned and not stored, and keys are held as an attribute of the image record.
